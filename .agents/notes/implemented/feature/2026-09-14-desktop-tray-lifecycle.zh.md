# Agent Note: 生命周期长于桌面窗口的托盘

Status: implemented

[English](2026-09-14-desktop-tray-lifecycle.md) | 中文

## Problem

桌面壳在最后一个窗口关闭时就结束运行，因此想要让 dsh 宿主继续运行的用户——正在进行的轮次、长时间的工具调用、插件安装——不得不把窗口留在屏幕上。窗口是壳唯一的表面，而回到宿主的每条路径都要经过它。

关闭改为隐藏需要一个「隐藏到哪里」的答案，否则进程会继续运行却没有办法重新显示它、没有办法退出它，也没有任何它仍在运行的证据。

## Decision

安装一个托盘图标，并让它拥有这次运行的生命周期：关闭主窗口只是隐藏它，只要托盘还在，`window-all-closed` 就不会退出应用，托盘菜单则是回到应用的路径——依次为「显示」「检查更新…」「退出」。

### 菜单从何而来

`src/tray.ts` 拥有菜单包含哪些条目以及它们的顺序；壳拥有每个条目做什么，把条目 id 映射到 `focusPrimaryWindow`、既有的更新检查，以及一个设置 `before-quit` 处理器所读标志的退出。这个划分的两半都有覆盖：模块由自身 spec 覆盖，映射由壳的启动 spec 覆盖。

### 图标

图标是编译进壳的 PNG data URL，而不是从磁盘读取的文件。打包的 `files` 列表只包含编译后的 JavaScript 与 renderer，因此磁盘上的图片需要每个平台一条打包条目、一个在打包与开发布局中都能解析的路径，以及该文件的签名方案。解码已经位于 bundle 内的字节没有这些问题：`nativeImage.createFromDataURL` 在所有平台都可用，无需定位任何文件。

### 关闭与退出

窗口自身的 `close` 事件正是区分两者的地方。除非进程已经在退出，关闭只会隐藏窗口，因此显式退出、接受更新安装与致命启动路径都能通过。查询托盘的 `window-all-closed` 处理器保留了 macOS 自身的约定，而不是发明第二条平台规则。

## Alternatives considered

**仅保留菜单栏模式。** 本次改动中否决：托盘是对窗口的补充而不是替代，一个只有托盘菜单作为表面的壳无法编写消息。

**窗口关闭即退出，并以隐藏状态启动。** 否决：一个没有可见表面、又不是用户要求保留的进程，与一个退出失败的进程无法区分。

**把托盘图标文件放在 `apps/desktop/assets/` 下。** 否决：它需要一条 `files` 条目、一个在打包与开发布局中都能解析的路径常量，以及每个目标的图标格式。托盘只有 16–20 px，完全不需要设计师的资产管理流程。

**通过插件窗口响应托盘。** 否决：插件窗口是已安装插件的管理表面，并会随主窗口一起关闭；托盘比两者都活得久。

**托盘存在时注册进程级按住说话组合键。** 本次改动中否决：听写的按住说话是 Web GUI 拥有的页面级组合键，桌面壳再加一个会让同一手势出现两个拥有者。

## Consequences

壳现在有两个生命周期不同的表面：窗口可以被隐藏而托盘仍在，因此任何假定窗口可见的未来功能都必须说明它指的是哪种状态。退出不再是无需窗口即可触达宿主的唯一方式，托盘也成为后台功能对外呈现的位置。

在不提供托盘的桌面环境中——某些 Linux 会话——图标可能不显示，此时应用会在没有可见表面的情况下运行。桌面版发布不面向 Linux，且窗口的关闭处理器无论如何都会注册，因此那里的行为属于平台而不是壳。

覆盖率验证了菜单条目及其顺序、带解析后提示与菜单的托盘创建、关闭时隐藏而非退出、点击托盘恢复窗口、菜单中的退出，以及窗口集合为空时运行仍在继续。
