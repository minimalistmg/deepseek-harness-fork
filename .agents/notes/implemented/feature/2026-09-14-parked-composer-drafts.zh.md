# Agent Note: 以 store 与座位组合实现输入框暂存草稿

Status: implemented

[English](2026-09-14-parked-composer-drafts.md) | 中文

## Problem

正在编写消息的用户常常会中途产生另一个想法：输入框里的消息并不是他想接下来发送的内容，而清空输入框只有两种办法——发送它，或者丢弃它。产品排除了第三种可能，即同时保留多份草稿——因为 Web GUI 的草稿是输入框镜像的单个按会话值，而发送队列保存的是将要发送的消息，而不是不打算发送的消息。

被卡住的问题是：暂存草稿应该存在哪里。输入框草稿是浏览器状态（`ConversationStoreState.draft`），发送队列是持久的宿主状态，两者都无法承载「用户搁置的草稿」。

## Decision

新增 `@deepseek-ai/dsh-client-ui-holds`，其草稿保存在一个按会话的 `defineStore` 实例中，由 `conversation.input.left` 中的控件与 `conversation.input.dock` 中的暂存区渲染。

暂存是浏览器状态而不是会话事件，因为它不是模型可见输入：只有用户发送它时才会到达模型，走的是手动输入消息完全相同的提交流程。store 通过共享快照引擎持久化，其 per-Scope 键是 store 自身名称加上会话 id，因此单个会话的暂存内容在刷新后依然存在，无需插件自有的文件或宿主路由。

同一个 handle 传给两处注册。框架按 handle × scope 生成实例，这正是控件与暂存区操作同一批草稿的原因；在 `apply` 内跨注册共享 handle 是两个入口共享状态的规范做法。

### 座位选择

控件占据 `conversation.input.left`，而不是语音座位与模型座位共享的右侧行：暂存是用户在编写前就会触达的左侧操作，而右侧行属于发送。

### 发送做了什么

发送通过 `inputActions.setDraft` 把暂存文本写入输入框，再通过 `inputActions.submit` 提交，并删除该行。因此暂存区不与任何会话服务交互：命令声明、忙碌会话与乐观发送都在输入状态机内部解决，被拒绝的提交通过输入框自身的通知显示，与手动输入的消息完全相同。这也是该行会立即从列表消失的原因：暂存区不保存在途状态，因为提交平面已经拥有该状态。

### 拒绝无法暂存的草稿

暂存值是文本。暂存带附件的草稿会清空输入框并丢弃浏览器持有的文件对象，且无从恢复，因此当 `attachmentIds` 非空时控件会拒绝，并在提示中说明原因。同样的推理也让控件拒绝空草稿，否则会暂存一行空内容。

### 调整顺序

调整顺序是同一个操作、两种手势：行之间的指针拖拽，以及聚焦把手上的上下方向键。只能拖拽的控件无法用键盘操作，而行位置是列表位置而非某个值，键盘用户必须能够改变它。

## Alternatives considered

**通过 Typert remote 实现宿主侧草稿存储。** 否决：暂存草稿不是持久产品数据，也不需要跨链路传输。浏览器本来就拥有输入框草稿，暂存属于同一类状态。

**把暂存控件放在右侧控件行。** 否决：那一行是输入框的发送侧，而暂存意图正好相反。它还会与语音座位的麦克风共享该行，两个不相关的控件争夺同一处狭窄空间，是输入框不应承担的布局决策。

**连附件一起暂存。** 暂不实现：图片草稿是浏览器 `File`，文件草稿是宿主回执，两者都无法以座位占用者可通过公开输入动作恢复的形式跨刷新存活。拒绝暂存才能保证暂存行就是用户会拿回的内容。

**把暂存放进发送队列。** 否决：队列中的行是会话将要投递的消息，每个都会记录为会话事件。可能永不发送的草稿不得进入日志。

**只用拖拽把手调整顺序。** 否决：这会让暂存区的操作只能靠指针完成，而行顺序本来只是普通数据。

## Consequences

输入框现在有两种让消息不发送的方式——暂存在暂存区，或排队等待投递——用户必须在两者间选择；README 说明了区别。暂存草稿的引用 chip 会被展平为剪贴板文本，因为那是输入状态投影出的内容，也是 `setDraft` 恢复的内容。

暂存内容是浏览器本地的：其他浏览器、其他机器或清除站点数据后都看不到它们，同一会话在两个浏览器中打开会保留两份互不相干的列表。覆盖率验证了 store 的五个动作、按会话隔离与重新加载、控件的拒绝与写入、暂存区的发送/编辑/删除/折叠与两种调整顺序手势，以及每处注册的销毁。
